# Perform-Task Skill

Express path for small tasks: compress the full lifecycle (plan → build → review) into a single command. The user's prompt is treated as the plan. Reuses the `build-executor` and `code-reviewer` agents **unchanged**.

## Instructions

### Step 1: Parse the Task

1. **Parse arguments**: "$ARGUMENTS" is the task description — a free-form prompt describing a small, scoped change.
   - If empty, jump to the **Fallback** section at the bottom.
2. **Infer a type prefix** from the task's nature, matching the plan skill's slug conventions (`chore` is additional here, for maintenance tasks that skip the full lifecycle):
   - `feat` — adds new behavior
   - `bug` — corrects a defect
   - `refactor` — restructures without behavior change
   - `chore` — maintenance, config, deps, docs
3. **Derive a short slug**: `<type>-<descriptive-slug>` (e.g., `bug-login-typo`, `chore-bump-eslint`).
4. **Size check**: if the task clearly spans many files, requires design decisions, or is ambiguous, jump to the **Fallback** section — do not force a large task through the express path.

### Step 2: Scaffold the Work Item

5. Create the `.dev/<slug>/` directory if it doesn't exist.
6. Initialize `.dev/<slug>/scratch.md` from `templates/scratch.md` if it doesn't exist.

### Step 3: Write a Minimal plan.md

7. Write `.dev/<slug>/plan.md` as a **prompt-as-plan**: minimal, but sufficient for `build-executor` to work through. Use exactly this skeleton:

   ```markdown
   > Generated by /perform-task — prompt-as-plan

   # Plan: [short task title]

   ## Goal

   [The user's prompt, cleaned up into 1–2 clear sentences.]

   ## Acceptance Criteria

   - [ ] [Concrete, testable condition derived from the prompt]
   - [ ] [Additional criterion only if the prompt implies one]

   ## Steps

   ### Step 1: [Title]

   [What to change and where, as specifically as the prompt allows.]

   ### Step 2: [Title] (only if needed)

   [...]

   ### Step 3: [Title] (only if needed)

   [...]
   ```

   Constraints on this plan:
   - **1–3 steps maximum.** If the task needs more, it belongs in `/plan`.
   - **No File-Action Index**, no Risks table, no Test Strategy, no Out of Scope, no Open Questions — none of the heavier sections from `templates/plan.md`. The marker line on top identifies it as an express plan.
   - Acceptance criteria must come **from the prompt only** — do not invent scope.
   - Name concrete file paths in steps when the prompt or a quick Glob/Grep makes them obvious; otherwise describe the change precisely enough for the executor to locate them.

### Step 4: Execute

8. **Spawn the `build-executor` agent** — unchanged, exactly as the build skill does — with the following prompt:
   > Work item: `.dev/<slug>/`
   > Execute the plan in `plan.md`.
   > Capture insights in `scratch.md` as you work.
   > Stop and report if any step fails or requires plan changes.

9. **Handle the build report**:
   - If all steps completed: proceed to Step 5.
   - If blocked: present the issue via `AskUserQuestion` — options: fix the plan and re-spawn, skip the step, or abort. For anything that reveals the task is larger than expected, recommend switching to `/plan <slug>`.

### Step 5: Review

10. **Determine the changed files** from the build report (or `git status --short` / `git diff --name-only` as a fallback).
11. Create `.dev/<slug>/reviews/` if it doesn't exist.
12. **Spawn the `code-reviewer` agent** — unchanged — with the changed file list and a note that this was a small express-path task. Collect its full output and write it to `.dev/<slug>/reviews/review-1.md`.

### Step 6: Report

13. **Update `.dev/<slug>/scratch.md`** with any insights or decisions that emerged.
14. **Report**:
```
## Task Complete: <slug>

**Done**: [1–2 sentence summary of what was changed]
**Files changed**: [list]
**Review**: CRITICAL: [N], HIGH: [N], MEDIUM: [N], LOW: [N]
Report saved: .dev/<slug>/reviews/review-1.md

Next steps:
- [If findings exist] `/review-fix <slug>` to address review findings
- `/triage` when done, to promote scratch insights to .ai-docs/
- Note: for multi-file features prefer `/plan` + `/build`
```

---

## Rules

1. **Small scoped tasks only** — one clear change, typically 1–3 files. Anything larger goes through `/plan` + `/build`.
2. **Never expand scope beyond the prompt** — the plan contains only what the user asked for; no drive-by refactors, no invented acceptance criteria.
3. **`build-executor` and `code-reviewer` are used unchanged** — this skill adapts its inputs to them, never the other way around.
4. **The marker line is mandatory** — `> Generated by /perform-task — prompt-as-plan` must be the first line of `plan.md`, so downstream skills can tell an express plan from a full one.
5. **Keep the plan minimal but executable** — every step must be concrete enough for `build-executor` to act without guessing.

## Fallback

If "$ARGUMENTS" is empty, or the task is too large or too ambiguous for the express path (many files, unresolved design choices, unclear requirements):

1. Ask via `AskUserQuestion`:
   > This task looks too [large / ambiguous] for the express path. How would you like to proceed?
   > 1. **Use /plan** — run the full planning cycle (recommended)
   > 2. **Proceed anyway** — I'll do my best with a minimal plan
   > 3. **Cancel**
2. If the user selects **Use /plan**, suggest the exact invocation: `/plan <task description>`.

## Examples

### Example 1 — Quick fix, clean run

**Invocation**: `/perform-task fix the off-by-one in the pagination footer — page count shows 0 when there is exactly one page`

**Step 1 — Parse**:
- Type inferred: `bug` (corrects a defect)
- Slug: `bug-pagination-count`
- Size check: single defect, one obvious location — express path is appropriate

**Step 2 — Scaffold**:
- Created `.dev/bug-pagination-count/`
- Initialized `scratch.md` from `templates/scratch.md`

**Step 3 — Minimal plan** written to `.dev/bug-pagination-count/plan.md`:

```markdown
> Generated by /perform-task — prompt-as-plan

# Plan: Fix off-by-one in pagination footer page count

## Goal

Fix the off-by-one error in the pagination footer where the page count displays 0 when there is exactly one page of results.

## Acceptance Criteria

- [ ] With exactly one page of results, the footer shows "1", not "0"
- [ ] Multi-page counts are unaffected

## Steps

### Step 1: Fix the page count calculation

Locate the pagination footer component (grep for the page-count rendering, e.g. `src/components/PaginationFooter`). Correct the calculation so a single full page yields 1 — likely a `Math.floor` that should be `Math.ceil` or a missing `|| 1`. Verify multi-page behavior is unchanged.
```

**Step 4 — Execute**: `build-executor` spawned:
> Work item: `.dev/bug-pagination-count/`
> Execute the plan in `plan.md`.
> Capture insights in `scratch.md` as you work.
> Stop and report if any step fails or requires plan changes.

Build report: 1/1 steps complete. Changed `src/components/PaginationFooter.tsx` (`Math.floor` → `Math.ceil`). Both acceptance criteria verified by existing unit tests.

**Step 5 — Review**: `code-reviewer` spawned on `src/components/PaginationFooter.tsx`. Output written to `.dev/bug-pagination-count/reviews/review-1.md`. Findings: 0 CRITICAL, 0 HIGH, 1 LOW (missing test case for zero results).

**Step 6 — Report**:
```
## Task Complete: bug-pagination-count

**Done**: Fixed off-by-one in pagination footer — single-page result sets now show "1".
**Files changed**: src/components/PaginationFooter.tsx
**Review**: CRITICAL: 0, HIGH: 0, MEDIUM: 0, LOW: 1
Report saved: .dev/bug-pagination-count/reviews/review-1.md

Next steps:
- /review-fix bug-pagination-count to address review findings
- /triage when done, to promote scratch insights to .ai-docs/
- Note: for multi-file features prefer /plan + /build
```
