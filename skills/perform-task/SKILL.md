# Perform-Task Skill

Express path for small tasks: compress the full lifecycle (plan → build → review) into a single command. The user's prompt is treated as the plan. Reuses the `build-executor` and `code-reviewer` agents **unchanged**.

## Instructions

### Step 1: Parse the Task

1. **Parse arguments**: "$ARGUMENTS" is the task description — a free-form prompt describing a small, scoped change.
   - If empty, jump to the **Fallback** section at the bottom.
2. **Infer a type prefix** from the task's nature, matching the plan skill's slug conventions (`chore` is additional here, for maintenance tasks that skip the full lifecycle):
   - `feat` — adds new behavior
   - `bug` — corrects a defect
   - `refactor` — restructures without behavior change
   - `chore` — maintenance, config, deps, docs
3. **Derive a short slug**: `<type>-<descriptive-slug>` (e.g., `bug-login-typo`, `chore-bump-eslint`).
4. **Size check**: if the task clearly spans more than 1–3 files, requires design decisions, or is ambiguous, jump to the **Fallback** section — do not force a large task through the express path.

### Step 2: Scaffold the Work Item

5. Set up the rest of the work item per `templates/work-item.md` steps 3–4: create `.dev/<slug>/` if it doesn't exist, and initialize `scratch.md` from `templates/scratch.md` if it doesn't exist. (Slug derivation was already done in Step 1 above, including the `chore` type this skill adds.)

### Step 3: Write a Minimal plan.md

6. Write `.dev/<slug>/plan.md` as a **prompt-as-plan**: minimal, but sufficient for `build-executor` to work through. Use exactly this skeleton:

   ````markdown
   > Generated by /perform-task — prompt-as-plan

   # Plan: [short task title]

   ## Goal

   [The user's prompt, cleaned up into 1–2 clear sentences.]

   ## Acceptance Criteria

   - [ ] [Concrete, testable condition derived from the prompt]
   - [ ] [Additional criterion only if the prompt implies one]

   ## Steps

   ### Step 1: [Title]

   [What to change and where, as specifically as the prompt allows.]

   ### Step 2: [Title] (only if needed)

   [...]

   ### Step 3: [Title] (only if needed)

   [...]

   ```loadout-handoff
   schema: 1
   artifact: plan
   produced_by: /perform-task
   work_item: .dev/<slug>
   lane: express
   verification: none
   next_command: /build
   next_arguments: .dev/<slug>
   ```
   ````

   Constraints on this plan:
   - **1–3 steps maximum.** If the task needs more, it belongs in `/plan`.
   - **No File-Action Index**, no Risks table, no Test Strategy, no Out of Scope, no Open Questions — none of the heavier sections from `templates/plan.md`. The marker line on top identifies it as an express plan.
   - Acceptance criteria must come **from the prompt only** — do not invent scope, and do not add drive-by refactors the prompt didn't ask for.
   - Name concrete file paths in steps when the prompt or a quick Glob/Grep makes them obvious; otherwise describe the change precisely enough for the executor to locate them.
   - The trailing `loadout-handoff` footer (field semantics: `templates/handoff-footer.md`) is mandatory, always the **last** thing in the file, with real `.dev/<slug>` values substituted for the placeholder above. This producer sets `verification: none` because this express plan carries no `**Validation**:` blocks of its own — `build-executor` recognizes the `> Generated by /perform-task — prompt-as-plan` marker (or `lane: express`) and verifies each step by judgement against `## Acceptance Criteria` instead (its Step 1.6 / Step 2.4 express-lane carve-out — dependency declared in both files). `next_command: /build` reflects what `/build .dev/<slug>` would do with this artifact if resumed independently, even though this skill also runs it inline via Step 4 below.

### Step 4: Execute

7. **Spawn the `build-executor` agent** — unchanged, exactly as the build skill does — with the following prompt:
   > Work item: `.dev/<slug>/`
   > Execute the plan in `plan.md`.
   > Capture insights in `scratch.md` as you work.
   > Stop and report if any step fails or requires plan changes.

8. **Handle the build report**:
   - If all steps completed: proceed to Step 5.
   - If blocked: present the issue via `AskUserQuestion` — options: fix the plan and re-spawn, skip the step, or abort. For anything that reveals the task is larger than expected, recommend switching to `/plan <slug>`.

### Step 5: Review

9. **Determine the changed files** from the build report (or `git status --short` / `git diff --name-only` as a fallback).
10. Create `.dev/<slug>/reviews/` if it doesn't exist.
11. **Spawn the `code-reviewer` agent** — unchanged — with the changed file list and a note that this was a small express-path task. Collect its full output and write it to `.dev/<slug>/reviews/review-1.md`.

### Step 6: Report

12. **Update `.dev/<slug>/scratch.md`** with any insights or decisions that emerged.
13. **Report**:
```
## Task Complete: <slug>

**Done**: [1–2 sentence summary of what was changed]
**Files changed**: [list]
**Review**: CRITICAL: [N], HIGH: [N], MEDIUM: [N], LOW: [N]
Report saved: .dev/<slug>/reviews/review-1.md

Next steps:
- [If findings exist] `/review-fix .dev/<slug>/reviews/review-1.md` to address review findings
- `/triage .dev/<slug>/` when done, to promote scratch insights to .ai-docs/
- Note: for multi-file features prefer `/plan` + `/build`
```

## Rules

1. **The marker line is mandatory** — `> Generated by /perform-task — prompt-as-plan` must be the first line of `plan.md`, so downstream skills can tell an express plan from a full one.

## Fallback

If "$ARGUMENTS" is empty, or the task is too large or too ambiguous for the express path (many files, unresolved design choices, unclear requirements):

1. Ask via `AskUserQuestion`:
   > This task looks too [large / ambiguous] for the express path. How would you like to proceed?
   > 1. **Use /plan** — run the full planning cycle (recommended)
   > 2. **Proceed anyway** — I'll do my best with a minimal plan
   > 3. **Cancel**
2. If the user selects **Use /plan**, suggest the exact invocation: `/plan <task description>`.
